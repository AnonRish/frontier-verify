# Triton Inference Server Integration

## Phase 2: research only. Phase 3: a real, tested adapter -- against real OpenTelemetry spans, still without real Triton

Phase 2 researched Triton's current architecture and identified
`--trace-config mode=opentelemetry` (no model-repository change required)
as the least invasive integration point, but built nothing. Phase 3 built
`frontier_verify.emitters.otel_span.OTelSpanEvidenceAdapter` against the
**real** `opentelemetry-sdk` package and tested it against **genuine**
`ReadableSpan` objects generated by OTel's own SDK
(`tests/unit/test_otel_span_adapter.py`) -- not hand-rolled dicts
pretending to be spans. That is real progress on the OTel-consuming half
of this integration, honestly bounded below.

## What's real

- `OTelSpanEvidenceAdapter.on_span_end(span)` extracts model name/version,
  serving engine, workload/request id, and real start/end timestamps from
  an OTel span's attributes and converts them into an `EmittedExecution`,
  which any `EvidenceEmitter` (e.g.
  `frontier_verify.emitters.async_queue.AsyncQueueEvidenceEmitter`) can
  then submit asynchronously -- proven not to block, same latency-
  isolation property the generic Python integration already demonstrated.
- The attribute-name mapping is **configurable**
  (`attribute_map` constructor argument), not hardcoded, specifically
  because the next honest gap (below) means the defaults may be wrong.
- Missing/absent attributes degrade to explicit `"unknown-model"` /
  fallback values rather than raising -- tested directly
  (`test_adapter_falls_back_gracefully_when_expected_attributes_are_absent`).

## What's still NOT real, stated plainly

**Whether Triton's actual `--trace-config mode=opentelemetry` output uses
the attribute names this module defaults to
(`gen_ai.request.model`, `gen_ai.system`, `triton.request_id`) is
UNCONFIRMED.** Those defaults follow OpenTelemetry's published GenAI
semantic conventions where they plausibly apply, chosen as an
educated, sourced guess -- not verified against a live Triton instance,
because none exists in this environment. This is exactly why the mapping
is configurable rather than baked in: a real deployment should expect to
override it, not assume the defaults are correct.

No model-repository change, no `TritonPythonModel`, and no live Triton
process has been built or tested this phase -- this remains, honestly,
"a real consumer for a format Triton is documented to be able to
produce," not "a tested Triton integration."

## Design (updated)

```
triton-server --trace-config mode=opentelemetry \
               --trace-config opentelemetry,url=<otel-collector-endpoint>
                        |
                        v
          (OpenTelemetry Collector, real infrastructure,
           not part of this repository)
                        |
                        v
     OTelSpanEvidenceAdapter.on_span_end(span)   <- REAL, TESTED (this phase)
                        |
                        v
        AsyncQueueEvidenceEmitter.emit(...)      <- REAL, TESTED (relocated
                        |                            from the generic-wrapper
                        v                            example, now shared)
             POST /v1/evidence (async, non-blocking)
```

Wiring `OTelSpanEvidenceAdapter.on_span_end` into an actual OpenTelemetry
`SpanProcessor` or collector-consuming pipeline is NOT built this phase --
`on_span_end` is deliberately a plain method taking a span, kept separate
from any specific OTel wiring mechanism (a real `SpanProcessor` subclass,
a collector webhook, a batch file consumer) so the conversion logic itself
is testable without standing up that infrastructure. Building the actual
wiring is the concrete next step, not attempted here.

## Modes

Unchanged from Phase 2: `audit-only` first. Enforcement remains out of
scope until real verification assurance justifies it, which
`docs/assurance-model.md` still caps at L1.

## What's tested vs. not (updated)

**Tested, for real, against real OTel SDK objects**: span attribute
extraction, timestamp conversion, fallback behavior, custom attribute
mapping, and downstream async, non-blocking submission through the same
`AsyncQueueEvidenceEmitter` the generic integration uses.

**Not tested**: anything involving an actual Triton process, an actual
model repository, or an actual OpenTelemetry Collector. Also not
confirmed: the attribute-name assumptions above.

## Next step if picked up

Get access to a running Triton instance (does not require a GPU -- Triton
can serve CPU models), enable `--trace-config mode=opentelemetry` pointed
at a local OTel Collector, capture a handful of real exported spans, and
compare their actual attribute keys against `DEFAULT_ATTRIBUTE_MAP` in
`frontier_verify/emitters/otel_span.py` -- correcting the mapping (not the
adapter's logic, which this phase's tests already cover) is very likely
all that's needed once real spans are available to check against.
