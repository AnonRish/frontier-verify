# Trust Boundaries

Reviewed under the assumption section 23 of the brief names explicitly:
**the prover is malicious**. For every piece of data in the system, three
questions: what does the prover control, what does the verifier
independently control, what can neither side modify after the fact.

| Data | Prover controls | Verifier independently controls | Neither can modify after the fact |
|---|---|---|---|
| `ModelIdentity` digests | Entirely -- self-reported, no independent check | Nothing | Nothing (once submitted, tamper-evident via the receipt, but the CONTENT was never independently confirmed in the first place) |
| `RuntimeIdentity` | Entirely -- self-reported | Nothing | Same as above |
| `HardwareEvidence` (mock) | Entirely -- `MockAttestationProvider` fabricates by design | Nothing | Same as above |
| `HardwareEvidence` (real, once Phase 2+ hardware attestation exists) | Which physical machine runs the attestation | The hardware vendor's root of trust does the actual constraining, not the verifier or the prover -- see `docs/hardware/nvidia-attestation.md` | The GPU's own signed attestation report, once issued, given a real vendor implementation exists |
| `Evidence.created_at` | Entirely -- self-reported timestamp | The freshness WINDOW (`Policy.max_evidence_age_seconds`) | Nothing -- see `docs/threat-model.md`, question I |
| `evidence_id` | The prover chooses it | The verifier now rejects (409) a resubmission under the same id with different content (Phase 2 fix -- see `docs/adversarial-results.md`, attack #6) | The FIRST submission under a given id, once stored |
| `Policy` (which policy is applied) | Nothing -- policies are registered by whoever calls `/v1/policies/validate`, typically the verifier operator or auditor, not the prover | Which policies exist and their content | A policy, once validated and stored, until explicitly changed |
| `PolicyResult` (pass/fail) | Nothing directly, though it controls this indirectly by controlling the evidence fed into evaluation | The evaluation LOGIC (`frontier_verify/policies/evaluator.py`) | The result of a specific `evaluate()` call against specific inputs -- deterministic, reproducible by rerunning it |
| Verifier signing key | Nothing | Entirely -- see `docs/protocol/key-management.md` | The key material itself, absent a KeyProvider compromise |
| `Receipt` signature | Nothing | Entirely -- only the verifier's key can produce a valid signature | The signature, cryptographically, once issued (Ed25519, not forgeable without the private key) |
| `Receipt.limitations` | Nothing | Entirely -- generated by the verifier's own code at issuance time | Once signed, part of the tamper-evident receipt |
| Whether a workload was reported AT ALL | Entirely -- the prover can simply not submit evidence for something it doesn't want observed | Nothing currently -- this is exactly the gap `docs/threat-model.md` question E and `docs/network-evidence-protocol.md` describe as unsolved | N/A -- there's no independent record of the workload's existence to protect in the first place |

## Prover identity: a confirmed gap, not a built feature (Phase 5)

Section 17 of the Phase 5 brief asks whether one compromised role can
silently impersonate another. Checked directly against the code, not
assumed: **any holder of a valid `PROVER`-role API key can submit evidence
under any `ModelIdentity`/`RuntimeIdentity` it likes, with zero
cryptographic binding to a specific prover's own identity.**
`submit_evidence()` (`frontier_verify/api/main.py`) checks only that the
caller holds *a* `PROVER`-role key — the same bearer-token check every
other `PROVER` action uses — and nothing in `Evidence`
(`frontier_verify/evidence/models.py`) contains a prover-side signature at
all. If two organizations share a deployment with two different
`PROVER`-role keys, evidence submitted under either key is
indistinguishable in origin from the other's, and a leaked key lets its
holder submit evidence that looks identical to legitimate submissions
from any other prover on that deployment.

This is a real gap, confirmed by inspection this phase, not a
hypothetical raised for completeness. **It is not fixed here.** A real
fix — provers holding their own signing keys, evidence carrying a
prover-side signature the verifier checks before accepting submission —
is a genuinely new cryptographic subsystem, not a bounded patch, and
building one now would be exactly the "broad feature-development cycle"
this phase's own brief says not to start. It's recorded here as a named,
confirmed, unfixed finding instead, which is what section 17 actually
asked this phase to produce.

## The one-sentence version

**Today, the prover controls the truth of everything except the receipt's
own integrity.** The verifier controls whether a given (self-reported,
unconfirmed) claim satisfies a given policy, and controls the
cryptographic integrity of its own output. Nothing in this system yet
independently confirms that what the prover reported actually happened --
that is the entire, explicit point of `docs/threat-model.md` and this
table both existing as separate documents instead of being summarized away
in a README.

## What changes this table, in order of how much it would change it

1. **Real hardware attestation** (Phase 2+, blocked on hardware access):
   moves one row -- `HardwareEvidence` -- from "prover controls entirely"
   to "hardware vendor's root of trust constrains it." Model and runtime
   identity remain entirely prover-controlled even after this.
2. **Independent recomputation** (Phase 6, `docs/research/recomputation.md`):
   would give the verifier partial, statistical independent confirmation
   that reported outputs match reported inputs for SAMPLED chunks --
   doesn't touch whether all relevant chunks were reported in the first
   place.
3. **Network evidence** (`docs/network-evidence-protocol.md`, deliberately
   NOT_IMPLEMENTED): the only entry on this list that would address "was a
   workload reported at all," and the only one requiring physical
   infrastructure this project cannot provide by writing more code.
